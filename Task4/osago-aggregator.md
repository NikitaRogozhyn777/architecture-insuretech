# Проектирование сервиса osago-aggregator для продажи ОСАГО

## 1. Требуется ли хранилище данных osago-aggregator?

**Да, требуется.** Необходимо хранить:
- Состояние заявок (created/pending/processed)
- Сопоставление внутреннего ID заявки с ID страховых компаний
- Полученные предложения от страховых компаний
- Таймстампы для контроля 60-секундного таймаута

**Рекомендуемая СУБД:** PostgreSQL (для согласованности с текущей инфраструктурой)



## 2. Общий процесс обработки заявки

Система работает по следующему сценарию:

1. Клиент отправляет запрос на расчёт ОСАГО через веб-интерфейс, который поступает в основной сервис `core-app`.

2. `core-app` создаёт событие о новом запросе и публикует его в Kafka. Это позволяет асинхронно обрабатывать заявки без блокировки основного потока.

3. Специализированный сервис `osago-aggregator` получает это событие, сохраняет информацию о заявке в базу данных и начинает взаимодействие со страховыми компаниями, отправляя им REST-запросы.

4. Для получения результатов `osago-aggregator` периодически опрашивает страховые компании, используя механизм long-polling. Это позволяет оперативно получать информацию о готовности предложений.

5. По мере поступления предложений от страховых компаний, `osago-aggregator` публикует их в Kafka в виде отдельных событий.

6. Основной сервис `core-app`, получая эти события, немедленно уведомляет клиента через технологию Server-Sent Events (SSE), обеспечивая реальное обновление данных в интерфейсе.

## 3. Механизмы обеспечения надёжности

### Ограничение частоты запросов (Rate Limiter)
На входе в `core-app` реализован механизм контроля частоты запросов - `Rate Limiter`, который защищает систему от перегрузок. Он ограничивает количество запросов от одного клиента в единицу времени, предотвращая злоупотребление ресурсами и обеспечивая стабильную работу сервиса для всех пользователей.

### Автоматический выключатель (Circuit Breaker)
При взаимодействии со страховыми компаниями используется паттерн `Circuit Breaker`. Он автоматически прекращает запросы к проблемным сервисам при превышении допустимого уровня ошибок, давая им время на восстановление. После периода ожидания система постепенно возобновляет взаимодействие, проверяя доступность сервиса.

### Повторные попытки и таймауты (Retry & Timeout)
Система предусматривает автоматические повторные попытки при временных сбоях связи со страховыми компаниями. Для каждого запроса установлен максимальный лимит времени ожидания (60 секунд), по истечении которого заявка считается завершённой с доступными на тот момент результатами. Это гарантирует, что клиент всегда получит ответ в разумные сроки, даже при частичных сбоях у партнёров.
