## Текущие проблемы архитектуры

**Текущая архитектура**
![Архитектура AS-IS](./InsureTech_C4_сontainer-diagram%20(Rogozhyn)-InsureTech%20(as-is).drawio.png)

1. **Монолитная структура core-app**
   - Сложность горизонтального масштабирования
   - Риск каскадных сбоев при увеличении нагрузки
   - Затруднённое внедрение изменений для новых интеграций

2. **Проблемы взаимодействия с ins-product-aggregator**
   - Синхронные запросы ко всем страховым компаниям создают bottleneck
   - Нет механизма кеширования/ретраев для ошибок интеграции
   - Увеличение времени ответа пропорционально числу партнёров

3. **Управление данными о продуктах**
   - Устаревание данных в локальных репликах (15 мин/24ч)
   - Отсутствие согласованности между репликами
   - Риск расхождений при частых обновлениях тарифов

## Риски при добавлении 5 новых страховых компаний

### Производительность
- **Линейный рост времени ответа ins-product-aggregator** (с 5 до 10 провайдеров)
- **Увеличение нагрузки на БД** из-за роста каталога продуктов
- **Рост latency в цепочке core-app → aggregator → партнёры**

### Надёжность
- **Увеличение вероятности частичных сбоев** (чем больше партнёров, тем выше шанс ошибки хотя бы у одного)
- **Отсутствие изоляции сбоев** - ошибка у одного партнёра может повлиять на всю систему
- **Риск перегрузки API партнёров** при синхронных массовых запросах

### Операционные риски
- **Усложнение мониторинга** 10 интеграций вместо 5
- **Рост объема ручной работы** при несоответствиях данных
- **Увеличение времени инцидентов** из-за сложности диагностики

## Проблемы данных
- **Отсутствие единого источника истины** для информации о продуктах
- **Потенциальные расхождения** между aggregator, core-app и ins-comp-settlement
- **Нет механизма обработки частых обновлений** тарифов от партнёров



# Оптимизация архитектуры InsureTech: Event-Streaming и Transactional Outbox

**Оптимизированная архитектура**
![Оптимизированная архитектура](./InsureTech_C4_сontainer-diagram%20(Rogozhyn)-InsureTech%20with%20Event%20Streaming.drawio.png)

## 1. Взаимодействия для перевода на Event-Streaming

### a) Обновление данных о продуктах
**Текущая реализация:**
- Периодические синхронные pull-запросы от core-app и ins-comp-settlement к ins-product-aggregator

**Предлагаемое решение:**
- **Event:** `ProductCatalogUpdated` (публикуется ins-product-aggregator при изменениях)
- **Подписчики:**
  - core-app (актуальные данные для клиентов)
  - ins-comp-settlement (актуальные тарифы для расчётов)

**Преимущества:**
- Немедленное распространение изменений
- Устранение проблем с устаревшими репликами
- Снижение нагрузки на ins-product-aggregator

### b) Оформление новых страховок
**Текущая реализация:**
- Синхронный вызов client-info в процессе оформления

**Предлагаемое решение:**
- **Event:** `PolicyIssued` (содержит все данные о страховке и клиенте)
- **Подписчики:**
  - client-info (для обновления данных клиента)
  - ins-comp-settlement (для учёта в месячном реестре)

**Преимущества:**
- Асинхронная обработка второстепенных задач
- Устойчивость к временной недоступности сервисов

### c) Формирование реестра выплат
**Текущая реализация:**
- Ежедневный синхронный запрос ins-comp-settlement → core-app

**Предлагаемое решение:**
- **Event:** `DailyPolicyBatch` (публикуется core-app в конце дня)
- **Подписчики:**
  - ins-comp-settlement (основная обработка)
  - Аналитические сервисы (дополнительно)

## 2. Применение Transactional Outbox

### Для каких операций подходит:
1. **Оформление страховок (core-app):**
   - Запись заявки в БД + событие `PolicyIssued` в outbox
   - Гарантирует что событие будет отправлено если транзакция успешна

2. **Обновление каталога продуктов (ins-product-aggregator):**
   - Обновление внутреннего состояния + событие `ProductCatalogUpdated`
   - Синхронизация между обновлением БД и уведомлением подписчиков

3. **Обновление клиентских данных (client-info):**
   - Изменение профиля + событие `ClientDataChanged`
   - Для синхронизации между сервисами
